# Scene image integration

Optional DM scene illustrations generated by a private, self-hosted Supra2-IMG service on the
operator's Tailscale tailnet. This is the Velvet-side guide: configuration, behavior, access,
security, prompting, and verification. The inference host itself is run from
[Supra2 service deployment](supra2-service-deployment.md); the original design rationale and
model facts are in [Image generation integration (proposed)](image-generation-integration.md),
and the historical handoff that stood the service up is
[Supra2-IMG inference setup prompt](supra2-inference-setup-prompt.md).

Two rules frame everything else:

- **Illustrations are illustrative, never authoritative.** Narration text owns what happened.
  An image can be missing, stale, off-model, or generation-failed and the turn is still
  complete. No image path may mutate campaign state or stand in for a narration, rule, or
  roll result.
- **The feature is server-mediated.** Browsers never call the image service. The Velvet server
  holds the base URL, the `Origin` value, the timeout, and the byte budget, reconciles jobs,
  and serves the stored bytes. The client only ever loads images from Velvet.

## Evaluation and production boundaries

- The lane is opt-in per installation: `VELVET_SCENE_IMAGES_ENABLED` must be the exact string
  `true` **and** a valid base URL must be configured. It is then still off until campaign
  settings enable it and choose `manual` or `automatic`. The client surfaces are additionally
  gated by the discovery flag `FEATURE_IMAGES`; flags are rollout controls, never security, so
  the server-side opt-in and settings remain the real boundary.
- The service URL is an operator-configured, server-side value. Velvet accepts `https://` to
  any host, and plain `http://` only for loopback, RFC1918 private, Tailscale CGNAT, and
  `*.ts.net` hosts. Public plain-HTTP destinations are rejected, not downgraded.
- The Supra2 service has no safety checker, no NSFW filter, and no watermarking. Restrict
  reachability to authorized tailnet identities (see the deployment runbook); do not treat a
  Tailscale tailnet as a moderation layer for prompts. Generated images are review candidates:
  nothing auto-publishes, and players only ever see the illustration selected for their
  session.
- This lane is self-hosted, so there is no per-call provider spend. The scarce resource is the
  single shared GPU lane; respect the service's busy behavior (below) rather than retrying
  through it.

## Configuration

All five keys are server-runtime and are read by `readSupra2ImageConfig`. Numeric values are
validated even while the lane is disabled, so a malformed value fails configuration instead of
being silently coerced. See [Operations](operations.md#environment) for the environment-table
classification.

| Key | Default | What it does |
| --- | --- | --- |
| `VELVET_SCENE_IMAGES_ENABLED` | Disabled | Exact lowercase `true` opts into the service. Any other value, including `TRUE`, leaves the lane off. Still requires a valid base URL. |
| `VELVET_SCENE_IMAGES_BASE_URL` | Unset | Service root. `https://` for any host; `http://` only loopback, RFC1918 private, Tailscale CGNAT, or `*.ts.net`. A trailing slash is trimmed. An invalid value disables the lane rather than falling back. |
| `VELVET_SCENE_IMAGES_ORIGIN` | Base URL origin | The `Origin` header sent on POST submissions because the service checks it as a request guard. Must be a bare `scheme://host[:port]`; credentials, paths, queries, fragments, and malformed values are rejected. Not an authentication credential. |
| `VELVET_SCENE_IMAGES_TIMEOUT_MS` | `120000` | Per-request deadline, integer 1000–600000 ms. A timeout on a submission that may have reached the service resolves to *uncertain*, never an automatic retry. |
| `VELVET_SCENE_IMAGES_MAX_BYTES` | `8388608` | Decoded byte budget per downloaded PNG, integer 1024–67108864 bytes. Enforced from `content-length` and again while streaming the body. |

There is deliberately **no token key**: the current service authorizes by tailnet identity, and
the adapter sends no `Authorization` header. Keep the base URL and origin out of client
bundles, logs, screenshots, and issue reports. The adapter's error types never include the base
URL, the origin value, response bodies, or prompts.

```bash
export VELVET_SCENE_IMAGES_ENABLED=true
export VELVET_SCENE_IMAGES_BASE_URL=https://your-inference-host.your-tailnet.ts.net
export VELVET_SCENE_IMAGES_ORIGIN=https://your-inference-host.your-tailnet.ts.net
# Optional overrides; the defaults above are the normal operating values.
export VELVET_SCENE_IMAGES_TIMEOUT_MS=120000
export VELVET_SCENE_IMAGES_MAX_BYTES=8388608
```

## Behavior

### Modes

Scene-image settings are strict and per campaign/session: `off` (default), `manual`, and
`automatic`. `enabled` is a separate gate, so a campaign can keep its art direction and presets
while images are off. Settings reject unknown keys and out-of-bounds values instead of
coercing them.

### Per-session limits, cooldown, and confirmation

- **Manual** generation is a deliberate DM action. It is bounded by the UI and the
  confirmation rule, not by the automatic limits.
- **Automatic** generation may emit at most `autoPerSessionLimit` images per session
  (0–32, default 1), and only after `cooldownSeconds` (0–3600, default 0) have elapsed since
  the most recent image. The pure decision helper returns one of `disabled`, `manual`,
  `session-limit`, `cooldown`, or `allowed`, so a caller always knows why nothing ran.
- **Automatic mode runs at most one image unattended.** A batch or grid of more than one image
  always requires explicit confirmation; with images `off`, any generation is opt-in and
  therefore confirmed.
- Batch planning expands `count × steps × guidance` up to a 128-image ceiling, with up to 32
  seeds and at most 8 values per steps/guidance axis, reusing the same seeds across every
  steps/guidance combination so a grid isolates the sampler change rather than the seed.

### Settings and presets

Settings cover `steps` (10–100), `guidance` (1–8), `seedMode` (`random` or `fixed` with a
signed 32-bit seed), `variationCount` (1–32), a campaign `stylePhrase`, keyed
`promptOverrides` (16 entries, 64-character keys, 500-character values), `bandwidth`,
`hideImages`, and `advancedOnlyDm`. Presets only set steps and guidance; they are workflow
defaults, not quality tiers.

| Preset | Steps | Guidance | Use |
| --- | --- | --- | --- |
| Preview | 10 | 3 | Fast rough blocking. |
| Balanced | 20 | 3 | Everyday default for a small, deliberate batch. |
| Reference | 50 | 3 | Slower default for a keeper image. |
| Guidance 1 (experimental) | 20 | 1 | Experimental; see the guidance-1 caveat below. |

### Deduplication cache

The cache key is a SHA-256 over the exact request material — `prompt`, `seed`, `steps`,
`guidance`, and an optional model version — rendered as `scene-image:<48 hex chars>`. An
unknown model version is omitted from the key material rather than replaced with a
placeholder, so it can never collide with a real version string. There is no clock or random
source in the key: the same request produces the same key within and across sessions. A cache
hit should serve the stored asset instead of submitting new GPU work, which is the primary
guard against duplicate generations from repeat clicks, reconnects, or two session tabs.

### Stale-scene protection

The play surface resolves one active scene key — the acting character's location, or the room
as a fallback — and every generation, gallery row, and selection is bound to it. A completion
is applied only if that scene is still current; a late result that arrives after the table has
moved on stays grouped under its own scene in the gallery but never overwrites the current
scene's selection, and it never replays a past turn. Combined with the no-blind-retry rule,
this is what makes it safe for generation to run asynchronously while play continues: the
image either lands on the scene it was made for or it does not land.

### Velvet HTTP contract

The campaign routes are frozen under
`/api/rpg/v1/campaigns/:campaignId/scene-images`. The client sends no provider credentials and
never calls the Supra2 service directly.

| Endpoint | Purpose |
| --- | --- |
| `GET .../settings` | Read `{ settings, revision }` for the campaign. |
| `PUT .../settings` | Replace settings with `{ expectedRevision, idempotencyKey, settings }`; the returned revision must advance and the returned settings must match the request. |
| `POST .../generate` | `202` `{ job, deduped }` for `{ sessionId, sceneKey, prompt?, seed?, steps?, guidance?, count?, auto?, idempotencyKey }`. `deduped: true` means the cache key matched and no new GPU work was submitted. |
| `GET .../gallery?sessionId=...` | `{ images }` for one session; each row carries `assetId`, `jobId`, prompt/seed/steps/guidance, projected status, timestamps, and `selected`, with an additive `sceneKey` when the sidecar exposes the job binding. |
| `POST .../select` | Choose one asset for one scene with `{ sessionId, sceneKey, assetId, expectedRevision, idempotencyKey }`; returns the selection and a receipt. |
| `GET .../jobs/:jobId` | Read one exact job while it is queued, running, ready, failed, or cancelled. |
| `GET .../assets/:assetId` | The image bytes, served by Velvet with campaign authorization (the same-origin URL an `<img>` loads). An optional `?sessionId=` restricts the response to an asset selected for that exact session. |

Job status in the Velvet projection is `queued`, `running`, `ready`, `failed`, or `cancelled`;
the route projects the sidecar's durable `submitted`, `done`, `uncertain`, and `stale`
states onto that vocabulary, the client tolerates unknown status strings, renders only rows
with an asset and a finished status, and never renders a queued, running, failed, or
cancelled row as an illustration.

### Retention and storage

Images are stored in a per-world sidecar (design name `image/presentation.sqlite`), not in
`velvet.sqlite`: directory `0700`, file `0600`, a bounded cache quota, expiry and prune rules,
and an owner lock. Assets are content-addressed by SHA-256; a request row captures the prompt
hash, model, seed, steps, byte size, and status. Serving is through Velvet with the same
campaign authorization rules used for published materials: an allowlisted content type
(`image/png`), `X-Content-Type-Options: nosniff`, private caching, and byte-range support. The
byte route is `GET /api/rpg/v1/campaigns/:campaignId/scene-images/assets/:assetId`.

The Supra2 service keeps only a bounded history of completed images (256 entries). Treat it as
a queue and a short-lived cache, not as storage: download promptly after the service job
reports `done`, store durably in the sidecar, and never hotlink the service from a browser.
This also means an asset survives a service restart, worker unload, or history eviction.

## Access

### DM controls and gallery

Generation controls, presets, seed/guidance/variation editing, batch confirmation, and the
review gallery are DM-only. `advancedOnlyDm` keeps the image controls out of the player-facing
UI. Generated results are candidates: the DM reviews them and selects one per scene, and no
image auto-publishes. The gallery groups images by scene, keeps queued, running, failed, and
cancelled rows out of the illustration slot, and marks the selected image for each scene.
Prompt construction is spoiler-filtered before it reaches the model: a `player` prompt sees
only `public` facts, a DM prompt may add `gm` facts, and `secret` facts are never auto-included
for either audience. Hidden entity names must be filtered out by the caller before prompt
building; `visibleNameFallback` exists to turn a fictional name into a visible characteristic
without echoing the name back.

### Player rendering and preferences

Players see the illustration selected for their session, served by Velvet with campaign
authorization. Each image has alt text and a loading state, and player alt text never repeats
the generation prompt (it may contain GM-only facts); only the GM view may include a clipped
prompt.

Campaign settings carry `bandwidth` (`full`, `reduced`, or `text-only`) and `hideImages` as
defaults, and each browser also keeps local display preferences that never leave the device:
hide images, reduced-bandwidth text-only mode (no image bytes are requested until the player
explicitly asks), and the gallery thumbnail size. Text-only is the graceful fallback and must
leave narration fully usable when images cannot or should not load.

Publication stays explicit and visibility-aware: an image attached to GM-only material must
never leak a GM-only identity to players, and the player projection only exposes what was
published.

## Security and robustness

### Exact request hygiene

| Operation | Headers |
| --- | --- |
| `GET /health`, `GET /api/status` | `Accept: application/json` |
| `POST /api/generate`, `POST /api/batch`, `POST /api/cancel` | `Accept: application/json`, `Content-Type: application/json`, `Origin: <configured origin>` |
| `GET /images/...` | `Accept: image/png` |

No credential is sent. Redirects are refused rather than followed, so a compromised or
misconfigured service cannot bounce the Velvet server to a different host. `GET /api/status`
history is shared with every other Studio user, so jobs are trusted only after they are
filtered to the IDs this caller submitted (`selectJobsByIds`); another user's prompts, seeds,
and results are never surfaced.

### Path and payload validation

Downloads accept only a same-service path rooted at `/images/`, with conservative path
segments and a `.png` suffix. Percent-encoding, queries, fragments, backslashes, control
bytes, alternate schemes, and traversal are rejected, and the final URL is re-checked against
the configured service origin. The response must be `image/png` (an absent content type is
tolerated), must start with the PNG magic bytes, and must stay inside the byte budget.

### Bounded backoff, never blind retry

A `429` is a definite rejection from the shared lane, so it is retried with bounded
exponential backoff plus jitter (default 3 attempts, 500 ms base, 4 s ceiling; the
`retry-after` value is captured). After the bound, the error surfaces as busy instead of
holding the lane. Timeouts, transport failures, and unreadable acceptance responses are
**not** retried: the submission may have reached the service, so the adapter reports
`uncertain`, and the caller either reconciles by polling the returned job IDs or discards the
submission. It must not resubmit automatically.

### Cancellation boundary

`POST /api/cancel` cancels **all queued service work for every Studio user**. It is exported
with an explicit never-wire warning: it must never be connected to a player action, per-request
cancellation, a campaign action, or any automatic recovery. It exists only for an operator to
clear a stuck shared lane. If one submission must be abandoned, discard it; do not cancel the
world.

## Prompting primer

### Assembly order

The prompt builder is deterministic and always assembles clauses in this order:

1. Location and focal feature (the subject).
2. Viewpoint and composition.
3. Lighting and weather.
4. Materials and environment details, including the audience-visible facts.
5. The campaign art style phrase (falling back to a generic consistent style).
6. Square-image constraints: one coherent scene with a strong silhouette, few recognizable
   features, no lettering or crowds, favor unoccupied scenery.

### Length and the 128-token encoder

Target roughly 50–80 words. The hard ceiling is 1000 characters, but the image encoder holds
only about 128 tokens, and the length estimator is a documented word/character heuristic, not
a tokenizer. If a report warns that the prompt is approximately over budget, shorten it — do
not trust the approximation to have found the exact truncation point.

### 256×256 composition

Native output is fixed at 256×256 with no resolution parameter. Favor a clear large shape and
a readable light-to-dark structure; avoid tiny objects, signage and lettering, large crowds,
and complicated action. Portraits, tokens, icons, props, and handout thumbnails fit the model
better than full scene art.

### Guidance semantics

Guidance 3 is the normal operating value. Guidance 1 is an **experimental** path: it skips the
unconditional prediction, so prompt adherence is markedly weaker. It is not a cheaper
equivalent of guidance 3, and its outputs should not be compared as if it were.

## Verification

Run the steps in order against the surfaces present in your build; each step lists the
observation that proves it.

1. **Configuration parses.** Set the five keys and restart the server. A malformed timeout or
   byte budget must fail loudly; an invalid base URL must leave the lane disabled rather than
   reachable.
2. **Service is reachable server-side.** With the adapter configured, a health check reports
   `ok: true` and a `release` string. Health is liveness only: it does not prove
   authorization or that the model is loaded.
3. **A manual DM generation runs.** Submit one prompt. Expect a job to move
   `queued` → `running` → `done`, the stored image to appear once `done`, and a
   first run after an idle unload to take longer (worker load) than the second.
4. **The player view is safe.** A player in the session sees the selected illustration with
   alt text and a loading state, and never the DM gallery or generation controls.
5. **Preferences work.** `hideImages` removes images from that client's transcript;
   `bandwidth: text-only` leaves narration readable with no image requests.
6. **Deduplication works.** Repeat the exact same prompt, seed, steps, and guidance; expect a
   `deduped: true` response and no new GPU job.
7. **Stale results do not overwrite.** Advance the scene while a generation is pending; the
   late result must not replace the current scene.
8. **Busy behavior is bounded.** Saturate the shared lane with concurrent submissions and
   confirm the server backs off on `429` and then reports busy rather than retrying forever.
9. **Cancellation stays out of player reach.** Confirm no player-facing action can reach
   `POST /api/cancel`.

### Troubleshooting

| Symptom | Likely cause | What to check |
| --- | --- | --- |
| Every submission reports busy | The shared GPU lane is saturated, or another Studio user's batch is in front of it. | `GET /api/status`: `busy`, queued job count, `worker.loaded`. Wait; do not cancel from a player action. |
| First image is much slower than later ones | Worker was cold and paid the model load. | `worker.loaded` before and after; the deployment runbook's cold-start note. |
| Authorization failures (401/403) | The Velvet server's tailnet identity is not the authorized login. | Fix the tailnet identity or ACL; never forge `Tailscale-User-Login` in application code. The adapter never sends it. |
| Protocol/schema error | The service `release` drifted from the adapter contract, or a proxy rewrote the body. | `GET /health` `release`; compare against the runbook's API section. |
| Payload too large | `VELVET_SCENE_IMAGES_MAX_BYTES` is below the returned PNG, or the response is not a PNG at all. | The byte budget and the response content type; raise the budget only within 64 MiB. |
| Timeout/uncertain submission | The request may have reached the service. | Reconcile the returned IDs through `/api/status`; do not regenerate blindly. |
| Images disappear from the gallery | The service history evicted them (256-entry bound). | Ensure the sidecar download happens promptly after `done`; stored assets are the durable copy. |
| Images never appear for a player | Bandwidth/text-only preference, hide-images preference, or unpublished material. | The client preferences and the publication state. |
