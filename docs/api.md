# API Reference

All routes are under `/api`. JSON write requests use `Content-Type: application/json`.

This page specifies HTTP behavior. Internal module locations below are implementation references only and do not add to or modify any API contract.

Structured and normal HTTP responses include `X-Request-Id`. Intentionally preserved raw pre-router malformed/overlong responses for unknown, legacy, and compatibility paths may omit that header; their existing raw compatibility behavior is not promoted to the structured response contract. A caller may supply an ID using `X-Request-Id` when it is 1-128 characters containing only letters, digits, `.`, `_`, `:`, or `-`; invalid values are replaced. Existing roleplay response bodies are unchanged and do not include request metadata. Structured campaign problem `instance` strings use safe route templates rather than concrete campaign IDs or caller-controlled lookalike suffixes and never include queries. Production automatic request logs keep method and an available safe route template only; when routing context is unavailable, the concrete path is omitted.

One preflight UoW snapshot resolves exact current position/name, campaign-character and actor ancestry, active timeline, and revision, then closes before ID generation or execution. A separately injected server generator creates one internal value used as command ID and idempotency key. The service constructs exact `roll_actor_dice` with `sourceTurnId: null` and invokes one factory-only executor once without retry. Under one `BEGIN IMMEDIATE`, that executor revalidates current `(created_at,id)` roster ordering, exact safe position/name, campaign-character identity, and actor ancestry before RNG, event ID, clock, or writes, then uses the unchanged generic atomic command path. Rename/insertion/deletion drift is typed 409; malformed persistence remains an internal error. The service validates receipt/event/result and returns `201 { "roll": { "character", "occurredAt", "result" } }` without `Location`. Other failures are neutral commit-ambiguous 500s requiring history refresh and no automatic retry. Responses are `no-store`; IDs/revisions, checks, DCs, narration, raw commands, and private state are excluded. HEAD and methods other than GET/POST remain absent.

The Slice 94 client accepts only that strict request-bound 201 as commit confirmation. It reports latest-history refresh separately and never identifies a particular identity-free entry as that roll or requires its presence. Network, 500, malformed 2xx/body, and other untyped outcomes remain ambiguous regardless of identical history projections. Exact `RPG_CAMPAIGN_DICE_BINDING_CONFLICT` 409 and `RPG_CAMPAIGN_NOT_FOUND` 404 are consumed as known non-commits because the documented service ordering classifies them before execution. Every issued POST still owns one fresh GET, and persistent status offers only a separate GET-only Refresh rolls action. Rapid manual Retry or Refresh pointer/key activation is synchronously limited to one GET until settlement without affecting reconciliation. This is client consumption of the existing statuses and does not change any HTTP semantics.

## M2.4 and M2.8-M2.11 RPG routes

The routes in this section use strict resource IDs and strict JSON objects: unknown fields reject, JSON writes require `application/json` with at most one optional `charset`, and all routes send at least `Cache-Control: no-store` on successes and scoped problems. The adventure-turn initial-reconciliation read instead sends `private, no-store`, and a successful adventure stream sends `private, no-store, no-transform`. Except for the three explicitly documented GET query schemas (campaign export, combat log, and initial-turn reconciliation), a raw query delimiter, including bare `?`, rejects. GET routes expose no HEAD alias. Missing, unavailable, or unauthorized resources are non-disclosing 404s; stale revisions and known state conflicts are 409s; malformed requests are 400 and unsupported media types are 415.

Every command request includes an `idempotencyKey`; every mutable existing aggregate also requires `expectedRevision`. An exact committed retry returns the immutable prior result/receipt without advancing revision or repeating effects. Changed key reuse conflicts. Receipts expose `{ idempotencyKey, revisionBefore, revisionAfter, occurredAt }`, with `revisionAfter = revisionBefore + 1`; encounter creation is the exception exposed without a receipt and creates revision 1. An unexpected 500 or lost response is commit-ambiguous: reconcile with the authoritative GET and never retry automatically. Route parameters own campaign, actor, encounter, combat, quest, faction, NPC, and storyline identity; bodies cannot select the trusted-local principal.

### Adventure turns and generation drafts (M2.11)

Requires `FEATURE_RPG_CAMPAIGN=true` and `FEATURE_RPG_MECHANICS=true`, with fixed trusted-local `local-owner` on the default loopback listener. Caller-supplied authorization and principal headers are ignored; this is not remote authentication. Feature denial occurs before query, path, media, body, or repository access. Every success and scoped problem is at least `Cache-Control: no-store`; the initial-reconciliation GET uses `private, no-store`, and a successful stream uses `private, no-store, no-transform`. Only the exact initial-reconciliation query schema accepts a query; every other route rejects any raw query delimiter. GET has no HEAD alias, writes require exact JSON with at most one optional `charset`, and all objects are strict.

| Method | Route | Strict request | Success |
| --- | --- | --- | --- |
| `GET` | `/rpg/v1/campaigns/:campaignId/rooms/:sessionId/play-bootstrap` | No query/body; strict campaign ID and once-decoded opaque, untrimmed legacy session ID | `200 { campaignId, sessionId, expectedRevision, session, principal, playableActors }` |
| `POST` | `/rpg/v1/adventure-turns/stream` | Initial `{ campaignId, sessionId, actorId, declaration, expectedRevision, idempotencyKey }`, narration derivative `{ variant: "narration-retry"|"narration-swipe", campaignId, sessionId, actorId, priorTurnId, expectedRevision, idempotencyKey }`, or resume `{ resumeToken }`; variants cannot overlap | `200` SSE with `X-Adventure-Turn-Id` |
| `GET` | `/rpg/v1/adventure-turns/reconcile-initial?campaignId=...&sessionId=...&actorId=...&idempotencyKey=...` | Exactly one each of the four strict query fields and no body | `200 { result: AdventureTurnGetResponse | null }` |
| `GET` | `/rpg/v1/adventure-turns/:turnId` | No query/body | `200 { turn, proposals, confirmation, receipts, narrationStatus, resumeToken? }` |
| `POST` | `/rpg/v1/adventure-turns/:turnId/confirm` | `{ proposalIds, decision: "approve"|"reject", expectedRevision, idempotencyKey }` | `200 { turn, resumeToken? }` |
| `POST` | `/rpg/v1/generation-drafts` | `{ campaignId, kind, brief, constraints, idempotencyKey }` | `201 { draft, provenance, changes, validationIssues }` |
| `GET` | `/rpg/v1/generation-drafts/:draftId` | No query/body | `200 { draft, provenance, changes, validationIssues }` |
| `POST` | `/rpg/v1/generation-drafts/:draftId/apply` | `{ selectedChanges, expectedRevision, idempotencyKey }` | `200 { draft, application, receipts }` |

The play bootstrap is an authoritative role-safe read for the fixed local principal. `session` is exactly `{ attached: true, attachedAt, active, adventureEligible }`; `principal` is exactly `{ role, control }`, with owner/GM mapped to `all`, player to `controlled`, and observer to `none`; `playableActors` contains at most 12 session-order `{ actorId, name }` values, exposing all actors for owner/GM, only locally controlled actors for player, and none for observer. The opaque session ID is preserved without trimming or resource-ID normalization. Adventure eligibility is true only for a published campaign, an active non-stopped attached session, and a session ID that also satisfies the strict resource-ID requirement of the stream. Missing campaign, denied/stale authority, absent or detached room, and unavailable play state are non-disclosing `404 RPG_CAMPAIGN_PLAY_NOT_FOUND`; malformed campaign or session path values use that same 404; a query is `400 RPG_INVALID_REQUEST`; feature denial and unsupported methods are `404 RPG_ROUTE_NOT_FOUND`; corrupt ancestry, ownership, session, participant, actor/controller state, response-shape failure, request/output mismatch, and repository failures are redacted `500 RPG_INTERNAL_ERROR`.

The initial stream declaration is trimmed, nonblank, and at most 8,000 characters; `expectedRevision` is the observed campaign administration revision. Narration retry/swipe requests contain no declaration: they bind a new narration-only turn to one exact terminal prior turn with the same campaign, session, and actor, reuse its declaration and durable receipts, and never rerun mechanics. `proposalIds` and `selectedChanges` are nonempty unique arrays, bounded to 32 and 64 respectively. Confirmation `expectedRevision` is the observed turn revision; apply `expectedRevision` is the observed draft revision. Initial creation, narration derivatives, confirmation, draft creation, and draft apply are idempotent under their supplied key: an exact committed retry returns the durable prior result without repeating effects, while changed key reuse, stale revisions, expired confirmation, unknown selected changes, or incompatible durable state returns 409. Draft apply durably performs review then apply, advancing a fresh staged draft by two revisions. No write is automatically retried.

The public `turn` field order is `{ turnId, campaignId, sessionId, actorId, mode, priorTurnId, declaration, state, revision, createdAt, updatedAt }`; `mode` is `original`, `narration-retry`, or `narration-swipe`, and `priorTurnId` is a strict ID or `null`. State is `declared`, `proposed`, `awaiting-confirmation`, `confirmed`, `mechanics-committed`, `narrating`, `completed`, `cancelled`, or `failed`. Each role-structural proposal is `{ proposalId, position, toolName, proposedAt, confirmation }`. Proposal confirmation is `{ state: "not-required" }`, `{ state: "pending", expiresAt }`, or `{ state: "decided", decision: "approved"|"rejected", decidedAt }`; decision identity, principal, expected revision, idempotency key, and expiry are absent. The aggregate confirmation is separately `{ state: "none" }`, `{ state: "pending", proposalIds, expiresAt }`, or `{ state: "decided", decisions: [{ proposalId, decision, decidedAt }] }`. Public receipts are `{ commandId, proposalId, linkedAt }`, and narration status is `{ status, text }`, where status is `none`, `pending`, `in-progress`, `completed`, or `failed` and text is nullable. Timeline identity, campaign revision, provider-call metadata, tool arguments, and proposal execution bindings are structurally absent from the HTTP turn projection. Proposal execution bindings are private server/repository state and are not an HTTP contract.

SSE opens with `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: private, no-store, no-transform`, `Connection: keep-alive`, `X-Accel-Buffering: no`, and the strict durable turn identity in `X-Adventure-Turn-Id`. The identity header is set before SSE framing for initial, narration-derivative, and resume requests, so it remains the reconciliation key if no body frame arrives. Each data frame uses the event name matching its JSON envelope and exact top-level field order `{ type, sequence, timestamp, payload }`; sequence starts at 0 for each connection and increments by one, and timestamp is canonical UTC. The closed event vocabulary and exact payload field order are:

| Event | Exact payload | Conditionality |
| --- | --- | --- |
| `turn_started` | `{ turn }` using the exact public turn projection above | Initial streams only, after durable create or recovery; never replayed on resume |
| `agent_status` | `{ status }`, where status is `planning`, `awaiting-confirmation`, `pending-mechanics`, or `narrating` | Coordination transitions actually reached by this connection; may occur more than once |
| `tool_proposed` | `{ proposal }` using the exact role-structural proposal above | Once per durable proposal on an initial stream; never replayed on resume |
| `confirmation_required` | `{ proposalIds, expiresAt }` | Only while one or more exact proposals are durably pending; followed by terminal `aborted` for that connection |
| `mechanics_committed` | `{ receipts }`, each `{ commandId, proposalId, linkedAt }` | Only when one or more durable proposal-linked receipts exist |
| `narration_delta` | `{ text }` | Only when nonempty persisted or deterministic fallback narration is available |
| `choice` | `{ choiceId, label }` | Validated non-executable vocabulary reserved for an explicit next choice; the current deterministic fallback lane emits no choices |
| `terminal` | `{ outcome, turn, narrationStatus, receipts }`, where outcome is `done`, `aborted`, or `error` | The single terminal event attempted for every opened connection; it may be undeliverable after disconnect |

Conditional events are not promises that every stream contains every event. In particular, an ordinary no-tool fallback turn emits `turn_started`, planning and narrating `agent_status` events, `narration_delta`, and `terminal`; it does not emit proposal, confirmation, mechanics, or choice events. A resume does not replay `turn_started` or `tool_proposed`. If approved work has no durable mechanics receipt yet, the stream reports `pending-mechanics` and terminates `aborted` rather than executing a tool. M2.11 does not implement the actual bounded tool bridge.

The server writes `: heartbeat` SSE comments every `VELVET_SSE_HEARTBEAT_MS`, defaulting to 15 seconds and falling back to that value when the configured interval is non-finite or non-positive. Delivery disconnect does not roll back or cancel deterministic durable orchestration; clients must use the no-store turn GET to reconcile. Durable turns, decisions, narration, and proposal-linked receipts survive process restart. Both confirmation POST and turn GET return the same optional `resumeToken` when an approved or rejected durable batch decision is resumable, allowing either lost confirmation outcome to be recovered after restart; the token is absent outside resumable states. The opaque bounded token is supplied only in the strict resume JSON variant, must never be placed in a URL or log, and must be treated as a secret continuation credential bound to the durable decision and fixed local principal. Resume can reconcile a crash-visible mechanics receipt link before narration without rerunning the mechanics command.

`GET /rpg/v1/adventure-turns/reconcile-initial` is the read-only idempotency locator for an initial `original` turn. Its exact strict query is `{ campaignId, sessionId, actorId, idempotencyKey }`; missing, duplicate/array-valued, unknown, malformed, or extra query data returns `400 RPG_INVALID_REQUEST`. A visible exact match returns the full `AdventureTurnGetResponse`, including a recoverable `resumeToken` when available. `{ result: null }` means no matching turn is currently visible under the fixed local authority, active timeline, eligible campaign/session/actor ancestry, and original-mode binding; it is race-ambiguous with an in-flight initial stream and does not prove non-commit or permit an automatic POST retry. Feature denial and unsupported methods are `404 RPG_ROUTE_NOT_FOUND`; attributable authorization/unavailability remains non-disclosing, and unexpected repository or projection failures are redacted `500 RPG_INTERNAL_ERROR`. Routed successes and scoped problems use `Cache-Control: private, no-store` and the static safe problem instance `/api/rpg/v1/adventure-turns/reconcile-initial`, never query values or a parameterized turn route.

Generation kind is exactly `encounter`, `location`, `npc`, `faction`, `quest`, `storyline`, or `content-pack`; `brief` is trimmed, nonblank, and at most 8,000 characters, and `constraints` contains at most 64 trimmed nonblank strings of at most 1,000 characters. The M2.11 create lane is deterministic user-brief fallback, not provider generation. Its exact provenance is `{ source: "user-brief", method: "deterministic-fallback", applicationScope: "draft-review" }`; each change is `{ changeId, summary, content: { brief, constraints } }`; each validation issue is `{ path, code, severity, message }`. Draft field order is `{ draftId, campaignId, kind, state, revision, createdAt, updatedAt }`, with state `staged`, `in-review`, `approved`, `rejected`, `applied`, or `cancelled`.

Generation apply accepts only known staged change IDs and returns `application: { scope: "draft-only", campaignDomainMutated: false }` plus exactly one draft receipt `{ receiptId, reviewDecisionId, scope: "draft-only", selectedChanges, appliedAt }`. It is draft-only review sealing: it does not create a campaign command receipt and does not mutate campaign-domain content. Actual tool bridging, content generation, and campaign-content application remain M4.2, M4.5, and M4.6 respectively.

Malformed requests return `400 RPG_INVALID_REQUEST`; wrong write media returns `415 RPG_UNSUPPORTED_MEDIA_TYPE`; disabled or unsupported routes return `404 RPG_ROUTE_NOT_FOUND`. Missing or denied turns return `404 RPG_ADVENTURE_TURN_NOT_FOUND`; stale turns return `409 RPG_ADVENTURE_TURN_STALE`; expired or conflicting turn commands return `409 RPG_ADVENTURE_TURN_CONFLICT`. Missing or denied drafts return `404 RPG_GENERATION_DRAFT_NOT_FOUND`; stale drafts return `409 RPG_GENERATION_DRAFT_STALE`; draft conflicts return `409 RPG_GENERATION_DRAFT_CONFLICT`. Problem instances use only safe route templates and never echo IDs, queries, bodies, tokens, tool arguments, or private bindings. Unexpected repository, persistence, output, or stream-setup failures are redacted `500 RPG_INTERNAL_ERROR`. A lost response, malformed terminal frame, disconnect, or unexpected 500 is write-ambiguous: reconcile with the authoritative no-store turn or draft GET before any manual action and never automatically repeat the write. Stream-side failures attempt terminal `error` with the latest durable projection when the connection and state remain available.

| `DELETE` | `/memories/:id` | Soft-forget a memory |

Memory kinds are `fact`, `preference`, and `event`. Manual memories default to approved. Concrete commands such as `remember that I prefer tea` extract up to three immediately approved memories because the command itself is explicit user approval. Natural disclosures such as `my name is...` or `I prefer...` become pending memories for review. In room turns, requests such as `remember your characters` select the whole cast up to the room cap and create an approved snapshot from each selected character's recent self-established details instead of storing the instruction text. Duplicate active memory content is ignored. Only approved, non-forgotten memories are included in prompts.

## Sessions

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/sessions?characterId=:id` | List all sessions or filter by participant |
| `POST` | `/sessions` | Create a single- or multi-character session |
| `POST` | `/sessions/solo` | Open or reuse a durable open one-character session |
| `GET` | `/sessions/:id` | Read a session and its active-branch messages |
| `GET` | `/sessions/:id/context` | Read editable authoritative and computed shared context |
| `PUT` | `/sessions/:id/context` | Update the session's authoritative current scene |
| `DELETE` | `/sessions/:id` | Permanently delete session history |
| `GET` | `/sessions/:id/messages` | Read active-branch messages |
| `POST` | `/sessions/:id/messages` | Add a user turn and generate one reply |
| `POST` | `/sessions/:id/stream` | Stream a user turn and reply over SSE |
| `POST` | `/sessions/:id/room-turn` | Route a message to pertinent participants and generate bounded sequential replies |
| `POST` | `/sessions/:id/room-continue` | Generate another bounded room exchange without a user message |
| `POST` | `/sessions/:id/continue` | Generate one character turn without a user message |
| `POST` | `/sessions/:id/stop` | Close a session and abort active generation |
| `POST` | `/sessions/:id/generation/cancel` | Cancel a matching streamed generation |

Create a legacy single-character session with:

```json
{ "characterId": "character-id", "title": "Optional title" }
```

Create a group session with:

```json
{
  "characterIds": ["aria-id", "noor-id"],
  "primaryCharacterId": "aria-id",
  "title": "Station evening",
  "presetId": "default"
}
```

Sessions support 1-12 unique participants. `characterId` remains in responses as a backward-compatible alias for `primaryCharacterId`; `participants` contains the hydrated character profiles. Participants cannot currently be changed after creation.

`POST /sessions/solo` accepts `{ "characterId": "..." }` and returns `{ session, messages, created }`. It reuses the newest open exact-solo session for that character or creates one. Group and closed sessions never qualify. This isolates conversation history but does not provide authorization.

Turn bodies accept optional `speakerCharacterId`; it must identify a session participant and defaults to the primary character. Character messages persist that identity as `speakerCharacterId`.

`POST /sessions/:id/continue` accepts `{ "speakerCharacterId": "..." }` and performs exactly one buffered character generation. With a configured provider, completion is followed by at most one bounded scene-synthesis request, for a ceiling of two provider calls.

`POST /sessions/:id/room-turn` accepts `{ "content": "...", "maxSpeakers": 4 }`. `maxSpeakers` is optional, defaults to 3, and is constrained to 1-6. With a usable provider, the server performs one routing request, validates the returned participant IDs, and generates one reply for each selected participant in order. Without one, routing uses the deterministic fallback without a provider call. Broad group language such as `everyone`, `guys`, `gang`, `both`, or `you two` expands selection when the cap permits. The first speaker initiates toward relevant selected participants; each later speaker receives the preceding character's exact reply and responds directly. Each selected participant replies at most once per round.

`POST /sessions/:id/room-continue` accepts optional `{ "maxSpeakers": 2 }`, constrained to 1-6. It requires at least two participants and a preceding character reply. No user message is created. Routing chooses pertinent speakers, and the server moves a participant other than the latest speaker to the first position when possible. Each generated reply directly receives and answers the preceding character's exact content. The call stops after the selected replies, uses the normal per-session generation lock, and returns `replies`, `selectedSpeakerIds`, `routing`, `messages`, and session state. The client implements autoplay by invoking this bounded endpoint sequentially for at most three configured rounds.

After each successfully completed room turn or continuation, the server performs at most one scene-synthesis request. A configured-provider room round therefore costs at most `1 routing + maxSpeakers generations + 1 synthesis`: eight calls at six responders. An initial round plus three autoplay rounds is capped at 32 calls.

Both room endpoints retain their JSON response by default. Send `Accept: text/event-stream` for progressive delivery. Room-turn event order is `user_message` → `state` → `room_reply`+ → `room_done`; room continuation starts at `state`. Each `room_reply` contains `{ reply, index, total }` and is emitted only after that attributed reply is persisted. `room_done` contains the complete JSON result for reconciliation.

## Prompt Templates

`GET /prompt-templates` returns 20 ordered template definitions covering character safety/persona/constraints/custom style/lore/memory/shared-context/final instructions, provider start-reply behavior, room routing, first/follow-up room speakers, single/room continuation, and factual scene synthesis. Each entry includes `id`, `label`, `description`, `defaultTemplate`, effective `template`, allowed `placeholders`, and `overridden`.

`PUT /prompt-templates/:id` accepts `{ "template": "..." }`. Unknown placeholders and templates over 64,000 characters are rejected. Send `{ "template": null }` to reset that layer to its application default. Overrides persist inside the harness settings JSON and require no schema migration. API keys are never included.

## Shared Context

`GET /sessions/:id/context` returns `{ context }` with combined authoritative `sourceOfTruth`, editable manual `editableSource`, model-produced `synthesizedSource`, their update timestamps, session state, participant names/archetypes, recent events, approved memories, triggered lore, and unresolved questions/goals. The synthesized state contains categorized current facts rather than copied chat lines. It is rewritten after completed turns from manual canon, its prior state, and recent active-branch messages. The same authoritative text is injected into every buffered and streamed character generation.

`PUT /sessions/:id/context` accepts `{ "sourceOfTruth": "..." }` as editable manual canon (up to 8,000 characters after trimming) and returns `{ source: { sourceOfTruth, updatedAt } }`. A later `GET /sessions/:id/context` combines manual canon with synthesized scene facts; manual canon has highest priority.

## Branches and Swipes

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/sessions/:id/messages/:mid/siblings` | List branch siblings and active selection |
| `POST` | `/sessions/:id/messages/:mid/activate` | Activate a message branch |

Swipes require a character reply directly parented by a user message. They inherit the original speaker unless another participant is supplied. Continuation replies cannot be swiped. Branch activation refreshes the active-branch summary and, when a usable provider is configured, synthesized scene state.

## End-to-End Contract Coverage


`VELVET_E2E_LIVE=1 npm run test:e2e:live` uses a temporary online backup of the configured application database. It verifies the configured provider through `GET /provider`, which must include `hasApiKey` and must not include `apiKey`, then exercises buffered and streamed turns, a two-speaker room turn, room continuation, synthesized factual context, and usage growth including `character_reply` and `scene_synthesis`. The workflow is capped at 12 provider calls. Tests use unique record names and remove only records they created in the cloned database.

## Internal implementation map (non-contractual)

`server/src/app.ts` owns Fastify construction, global request behavior, and plugin registration; route handlers are not implemented there. Legacy read/management handlers are split across focused plugins under `server/src/routes/roleplay/`. `server/src/routes/roleplay/interactions.ts` owns message, room-turn/continuation, streaming, cancellation, swipe, activation, branch, and single-continuation handlers. It delegates common buffered/streamed generation, scene synthesis, and summary updates to `generationService.ts`, while `generationRegistry.ts` owns process-local per-session exclusion and active-stream abort state shared with `sessionLifecycle.ts`.

RPG HTTP handlers remain under `server/src/routes/rpg/v1/`. All persistence consumers import the public `server/src/repo/index.ts` barrel; schema/migration and repository-domain ownership are documented in [repo-architecture.md](repo-architecture.md). These locations describe the current implementation only. The routes, methods, request/response shapes, status handling, and other contracts above are unchanged by this map.
