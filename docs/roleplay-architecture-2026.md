## Persona technique

- Treat character records as durable current profiles. Editing a character changes the profile used by new and resumed sessions; sessions do not snapshot persona fields.
- Re-inject persona constraints every turn in a fixed prompt layer.
- Prefer structured fields over long backstory prose to reduce persona drift.

## Memory technique

- Short-term: last N verbatim turns stay in context.
- Episodic: rolling summary per session, updated every few turns.
- Long-term writes remain reviewable: explicit remember commands and requested cast snapshots are immediately approved, while natural name/preference disclosures are captured as pending for review.
- Memory is reviewable, editable, approvable, soft-forgettable, and restorable in the current client.

## Scene-state technique

States: `setup -> active -> closed` exercised in the MVP; `paused`/`cooldown` exist in the `SceneState` type but have no transitions yet (`aftercare` still reserved).

- The state machine owns consent state; the model only narrates inside the current state.
- Missing consent is treated as denied.

## Conversation model

Messages form a per-session tree (`parent_id`), with swipe alternates grouped by `swipe_group_id`/`swipe_index`. Each session tracks `active_leaf_id`; history, prompt assembly, and summaries operate on the active root-to-leaf branch. Character messages carry `speaker_character_id`. Swipes require a character reply with a direct user parent and inherit that reply's speaker by default. Branching retries or edits a user turn and preserves speaker attribution.

Sessions have 1-12 legacy participants through `session_characters`, plus a primary character retained in `sessions.character_id` for backward compatibility. Each character-generation call targets exactly one participant; room routing and scene synthesis are auxiliary provider calls. `POST /api/sessions/:id/continue` creates one character turn without a new user message, enabling deliberate character-to-character dialogue without an automatic loop. A persisted present NPC is additional role-visible scene cast, not a legacy participant or autonomous speaker; campaign roster membership alone does not establish presence.

## Prompt orchestration skeleton

1. Default first-layer system guidance: fictional adults, consent, current state. This template is editable and is not an enforcement boundary; deterministic safeguards remain independent.
2. Participant cards: current profiles for every session participant, with one target speaker.
3. Active constraints: user boundaries and scene state.
4. Retrieved memory: the target speaker's approved facts, the session summary, and global or participant-scoped triggered lore.
5. Authoritative shared context: editable manual canon plus synthesized current scene facts, with manual canon taking precedence.
6. Recent dialogue window (active branch, last `harness.recentTurns`).

The completed campaign-aware context boundary uses this canonical authority order: safety and actor control; human-authored campaign canon and explicit overrides; committed mechanics and campaign events; the exact final player declaration; visible world, cast, quests, and legal actions; authorized private target facts; approved memories and visible lore; recaps and summaries; then generated suggestions. Visible cast includes only persisted present NPCs while the attached session is running, with locations only when visible to the role. Stopped at-stop cast history is not prompt-current, and the full campaign NPC roster is never inferred to be present. Lower layers cannot contradict or mutate higher layers.

## Historical production v13 to v14 SQLite rollout

1. Resolve the live database path (`$VELVET_DATA_DIR/velvet.sqlite`, otherwise `data/velvet.sqlite`), enable maintenance mode, block new writes, and let in-flight writers drain. While the database remains open, use SQLite's online backup API: `sqlite3 "$DB" ".timeout 10000" ".backup '$BACKUP'"`.
2. Verify the backup before rollout: `sqlite3 "$BACKUP" "PRAGMA quick_check; PRAGMA foreign_key_check; SELECT key,value FROM meta WHERE key IN ('schemaVersion','schemaRevision') ORDER BY key;"`. Require `quick_check` = `ok`, no foreign-key rows, and the expected v13 metadata. Stop every Velvet writer; never run v13 and v14 binaries concurrently. Repeat the backup if any write occurred after it.
3. Start exactly one v14 server. Repository startup performs the atomic migration; only after it succeeds, verify the live file reports schema version 14/revision 1 and run `PRAGMA integrity_check` plus `PRAGMA foreign_key_check`. Require `ok` and no foreign-key rows before restoring normal traffic or starting additional instances.
4. To restore, stop all writers, preserve the failed database for diagnosis, remove only its associated `-wal`/`-shm` files, copy the verified backup back to the original path, rerun the backup integrity queries, and start the previous v13 binary. Retry v14 later only as a new coordinated rollout; there is no down-migration.
